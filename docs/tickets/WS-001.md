# WS-001: Fix attack persistence on save

## Description

Attacks are lost on save — confirmed across 11/11 tested classes (G8 from UX Review 2). Resources, spells, and items persist fine, so the issue is specific to the attack save path. Likely a missing or incorrect field mapping in the PocketBase update call.

## Acceptance Criteria

- [x] Attacks persist across save/reload for all weapon types (melee, ranged, spell)
- [x] Custom attacks (homebrew) also persist
- [x] Existing characters with attacks don't lose data on next save
- [x] No regression in resource/spell/item persistence

The save path is identical for attacks and resources (both go through the same `update` + `save` functions).

### 2026-03-18 14:45 — developer
**Decision:** Root cause identified. The `attacks` JSON field was **never added to the PocketBase database**. The initial migration (`0001_initial_schema.js`) creates the characters collection without `attacks`. Subsequent migrations add `feats` and `featureChoices` but never `attacks`. PocketBase silently drops unknown fields on update, so attack data was sent correctly by the frontend but discarded by the database. On reload, the field returns null/missing, defaulting to `[]`.

The `setup-collections.sh` reference script does include `attacks` — the field was intended but the migration was missed.

Also found 9 other Character fields missing from migrations: `exhaustionLevel`, `personalityTraits`, `ideals`, `bonds`, `flaws`, `appearance`, `backstory`, `alliesAndOrganizations`, `additionalFeaturesAndTraits`. These would cause the same silent data loss.

## Resolution

**Root cause:** The `attacks` JSON field was never added to the PocketBase `characters` collection via migration. The initial schema (`0001_initial_schema.js`) omitted it. PocketBase silently drops unknown fields on update — so attacks were sent correctly by the frontend but discarded by the database on every save.

**Fix:** New migration `1773300000_add_missing_character_fields.js` adds `attacks` (and 9 other missing fields) to the characters collection. No frontend code changes needed — the React save path was correct all along.

**Why resources worked:** The `resources` field WAS included in the initial migration (line 268 of `0001_initial_schema.js`). The `attacks` field was simply missed.
